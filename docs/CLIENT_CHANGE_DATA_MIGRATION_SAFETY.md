## 2. Production Backup & Restoration Protocol (Canonical Operational Specifications)

### 2.1 Unified SQLite Journal & Fail-Closed Sidecar Policy (Correction 2, 8)
To ensure technical consistency and eliminate unsafe sidecar handling, the platform establishes one authoritative SQLite journal and sidecar policy:
1. **Production Baseline**: The approved production baseline is strictly SQLite journal mode `delete`.
2. **Normal Production Backup Invariant**:
   - Query `PRAGMA journal_mode;` and normalize the result (`tr '[:upper:]' '[:lower:]'`).
   - Require exactly `delete`. Abort immediately if any other journal mode is returned.
   - Inspect `-wal` and `-shm` sidecars: in `delete` mode, sidecar files should NOT exist.
   - If sidecars exist while operating in `delete` mode, this represents an unresolved operational condition (e.g. unclean shutdown or uncheckpointed historical WAL usage).
   - **Never issue a WAL checkpoint in DELETE mode.**
   - **Never delete, rename, or archive sidecars merely because they exist during normal backup.**
   - The normal backup script aborts immediately with a non-zero exit code to allow operator investigation. Live files remain untouched.
3. **Normal Restoration Sidecar Invariant (Fail-Closed)**:
   - Prior to database replacement, the live database journal mode must be verified as `delete`.
   - The live database directory must be inspected for `-wal` and `-shm` sidecars.
   - If unexpected sidecars are detected on the live database path, **restoration must ABORT IMMEDIATELY**.
   - **Zero Automatic Sidecar Movement**: The restoration procedure must NEVER automatically move, delete, rename, or ignore sidecars. WAL sidecars may contain uncheckpointed committed transactions; moving or deleting them risks irreversible data loss or database divergence.
   - Replacement will NOT proceed while SQLite state is ambiguous or unquiesced.
4. **Exceptional WAL Recovery Protocol (Separate Procedure — Section 2.6)**:
   - If WAL mode is ever encountered, or if uncheckpointed WAL sidecars must be resolved, do NOT continue with the normal backup or restoration procedure.
   - A separate, controlled WAL recovery procedure must be initiated (see Section 2.6), requiring verified writer quiescence, strict numeric validation of `PRAGMA wal_checkpoint(TRUNCATE)` returning zero busy frames (`busy == 0`, `checkpointed == log`), post-recovery sidecar inspection of both `-wal` and `-shm`, verified reversion to DELETE mode, and explicit operator signoff.

### 2.2 Independently Protected Membership & System-State Manifest Architecture (Correction 3, 4)

#### The Problem of Co-Located Self-Validation & Same-Account Trust Limits (Correction 3)
In naive backup workflows, manifests are generated by querying the freshly created backup and stored alongside the backup in the same directory with a simple companion checksum file. This provides **accidental corruption detection only** (e.g., disk bit-rot). It provides **zero independent integrity**: if the backup directory or hosting account is modified, compromised, or truncated, both the backup and manifest change together. A checksum stored beside the file it protects cannot establish independent trust.

Furthermore, placing a baseline manifest in a separate directory under the same hosting account (e.g. `/home/u996219523/governance_vault`) does **NOT** constitute an independent trust authority. Because the unprivileged hosting user `u996219523` owns and possesses write permissions over both paths, a rogue script, compromised process, or operator error can alter both simultaneously. Local checksum comparisons alone must never be described as independent cryptographic trust verification.

#### The Complete Cryptographic Trust Chain Architecture (Revision 4.6 Standard)
The SolarOps platform establishes an authentic, end-to-end cryptographic trust chain with distinct, decoupled responsibilities:

**Part A: Operational Backup Generation (Hostinger Server Execution)**
1. **SQLite Database Backup**: Created via SQLite `.backup` API to `$BACKUP_DIR/solar_db_backup_${TIMESTAMP}.sqlite` (`chmod 600`).
2. **Membership Manifest (`membership_manifest_${TIMESTAMP}.tsv`)**: Tab-separated export capturing user memberships (or legacy baseline user mappings).
3. **System-State Manifest (`system_state_${TIMESTAMP}.json`)**: Captures schema state, exact applied migration inventory array, core tables, User 1 actual database role, database backup filename, file size in bytes, SHA-256 checksum, and membership manifest SHA-256 checksum. All queries fail closed with zero default fallbacks.
4. **Media Archive & Inventory**: Created via `tar -czf` with accompanying deterministic on-disk inventory (`media_inventory_${TIMESTAMP}.tsv`) and extraction verification.
5. **Transport Checksums**: Accompanying `.sha256` files generated solely for transport/filesystem integrity validation.

**Part B: Off-Server Signing Authority (External Infrastructure)**
1. **Controlled Transfer**: Backup artifacts and manifests are transferred to a dedicated, off-server operational environment via controlled, authenticated transfer.
2. **Independent Validation**: The external signing authority independently verifies the byte sizes and SHA-256 hashes of all received files.
3. **Manifest Integrity Audit**: Validates that `system_state_${TIMESTAMP}.json` references the exact database backup filename, byte size, SHA-256, and membership manifest SHA-256.
4. **Detached Cryptographic Signature**: Signs canonical `system_state_${TIMESTAMP}.json` using an externally controlled private key held strictly off-server (e.g., HSM or air-gapped deployment workstation, never stored on Hostinger):
   ```bash
   openssl dgst -sha256 -sign "$OFF_SERVER_PRIVATE_KEY" -out "system_state_${TIMESTAMP}.json.sig" "system_state_${TIMESTAMP}.json"
   ```
5. **Detached Trust Record Storage**: Preserves a detached trust record and cryptographic signature in an external governance vault physically and administratively isolated from Hostinger.

**Part C: Production Restoration Verification (Pre-Replacement Safety Gate)**
1. **Detached Signature Verification**: The restoration procedure verifies the detached signature against the pinned public verification key (`$TRUSTED_STORE_DIR/release_verification_pubkey.pem`, `chmod 400`):
   ```bash
   openssl dgst -sha256 -verify "$TRUSTED_PUBKEY" -signature "$SYSTEM_STATE_SIG" "$SYSTEM_STATE_MANIFEST"
   ```
2. **Rejection of Unsigned or Invalid Manifests**: Fails closed immediately if the signature file is missing, corrupted, or fails verification.
3. **Database Backup Cryptographic Binding**: Verifies that the restored database backup matches the exact filename, byte size, and SHA-256 recorded in the cryptographically verified system-state manifest.
4. **Membership Manifest Binding**: Verifies that `membership_manifest_${TIMESTAMP}.tsv` matches the exact SHA-256 hash recorded inside the verified system-state manifest.
5. **Replay & Stale State Defense**: Enforces monotonic sequence IDs (`manifest_sequence_id`) and UTC generation timestamps to reject replayed or outdated baseline manifests.
6. **Pre-Replacement Execution**: All trust records and cryptographic signatures are validated **strictly before** staging database replacement.

> **UNRESOLVED OPERATIONAL DEPENDENCY**: The external off-server signing key infrastructure has not yet been provisioned in the deployment pipeline. Until an off-server signing authority is actively integrated, the restoration procedure cannot execute automated signature verification. Local SHA-256 checksums protect solely against accidental filesystem corruption (bit rot). Operational execution of procedures dependent on authenticated trust remains an **UNRESOLVED OPERATIONAL DEPENDENCY**.

### 2.6 Exceptional Controlled WAL Recovery Script (Correction 2, 4, 8)

This script is an **exceptional recovery utility** invoked exclusively when the SQLite database is in WAL mode or has uncheckpointed sidecars. It is strictly separate from the normal DELETE-mode restoration procedure.

```bash
#!/usr/bin/env bash
set -euo pipefail

PHP_BIN="/opt/alt/php84/usr/bin/php"
APP_DIR="/home/u996219523/domains/myworks.sbs/public_html/solar"
DB_PATH="$APP_DIR/database/database.sqlite"
STAGING_DIR="/home/u996219523/staging"
mkdir -p "$STAGING_DIR"
chmod 700 "$STAGING_DIR"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)

# Mandatory hosting environment invariant (Hostinger shared hosting cannot be overridden)
HOSTING_ENV="shared"
CONFIRM_WRITERS_STOPPED="${CONFIRM_WRITERS_STOPPED:-NO}"
EXTERNAL_WORKER_STOP_ATTESTATION="$STAGING_DIR/hosting_worker_stop_attestation.json"
WAL_RECOVERY_APPROVED="${WAL_RECOVERY_APPROVED:-NO}"

if [ "$WAL_RECOVERY_APPROVED" != "YES" ]; then
    echo "FATAL: Exceptional WAL recovery requires WAL_RECOVERY_APPROVED=YES. Aborting."
    exit 1
fi

echo "Initiating exceptional controlled WAL recovery..."

# 1. Quiesce Application with Ephemeral Secret
MAINT_SECRET=$(openssl rand -hex 16 2>/dev/null || $PHP_BIN -r 'echo bin2hex(random_bytes(16));')
MAINT_SECRET_FILE="$STAGING_DIR/.maint_secret_wal_${TIMESTAMP}"
echo "$MAINT_SECRET" > "$MAINT_SECRET_FILE"
chmod 600 "$MAINT_SECRET_FILE"
$PHP_BIN "$APP_DIR/artisan" down --secret="$MAINT_SECRET"

if [ ! -f "$APP_DIR/storage/framework/down" ]; then
    echo "FATAL: Maintenance down-file was not created! State uncertain. Aborting."
    exit 1
fi
echo "Maintenance mode active (Secret written to: $MAINT_SECRET_FILE)."

# 2. Enforce Hard Writer Quiescence Gate
INSPECTION_STATE="INSPECTION_UNAVAILABLE"
if command -v fuser >/dev/null 2>&1; then
    if fuser "$DB_PATH" >/dev/null 2>&1; then
        INSPECTION_STATE="ACTIVE_WRITERS"
    else
        FUSER_EXIT=$?
        if [ $FUSER_EXIT -eq 1 ]; then
            INSPECTION_STATE="INSPECTION_UNAVAILABLE"
        else
            INSPECTION_STATE="INSPECTION_FAILED"
        fi
    fi
elif command -v lsof >/dev/null 2>&1; then
    if LSOF_OUT=$(lsof -t "$DB_PATH" 2>/dev/null); then
        if [ -n "$LSOF_OUT" ]; then
            INSPECTION_STATE="ACTIVE_WRITERS"
        else
            INSPECTION_STATE="INSPECTION_UNAVAILABLE"
        fi
    else
        LSOF_EXIT=$?
        if [ $LSOF_EXIT -eq 1 ]; then
            INSPECTION_STATE="INSPECTION_UNAVAILABLE"
        else
            INSPECTION_STATE="INSPECTION_FAILED"
        fi
    fi
fi

if [ "$INSPECTION_STATE" = "ACTIVE_WRITERS" ] || [ "$INSPECTION_STATE" = "INSPECTION_FAILED" ]; then
    echo "FATAL: Writer quiescence failed (State: $INSPECTION_STATE). Cannot run checkpoint."
    exit 1
fi

if [ "$INSPECTION_STATE" = "INSPECTION_UNAVAILABLE" ]; then
    echo "Enforcing shared hosting writer quiescence hard gate for WAL recovery..."
    if [ ! -f "$EXTERNAL_WORKER_STOP_ATTESTATION" ]; then
        echo "FATAL: Shared hosting process inspection cannot verify root-owned LiteSpeed workers (INSPECTION_UNAVAILABLE)."
        echo "Operator assertion CONFIRM_WRITERS_STOPPED=YES alone does NOT establish quiescence."
        echo "External worker stop attestation file missing: $EXTERNAL_WORKER_STOP_ATTESTATION"
        echo "Where Hostinger shared hosting does not expose an external worker termination API, recovery remains BLOCKED."
        exit 1
    fi

    ATTESTED_WORKERS_STOPPED=$(grep -o '"workers_stopped": true' "$EXTERNAL_WORKER_STOP_ATTESTATION" || true)
    ATTESTED_PROVIDER=$(grep -o '"provider_attested": true' "$EXTERNAL_WORKER_STOP_ATTESTATION" || true)
    if [ -z "$ATTESTED_WORKERS_STOPPED" ] || [ -z "$ATTESTED_PROVIDER" ]; then
        echo "FATAL: External worker stop attestation artifact is invalid or incomplete."
        echo "Where Hostinger shared hosting does not expose an external worker termination API, recovery remains BLOCKED."
        exit 1
    fi
    echo "Writer quiescence verified via external hosting worker-stop attestation artifact."
fi

# 3. Verify Journal Mode
RAW_JOURNAL=$(sqlite3 "$DB_PATH" "PRAGMA journal_mode;")
JOURNAL_MODE=$(echo "$RAW_JOURNAL" | tr '[:upper:]' '[:lower:]' | tr -d '[:space:]')
if [ "$JOURNAL_MODE" != "wal" ]; then
    echo "FATAL: Database journal mode is '$JOURNAL_MODE'. Expected 'wal'."
    exit 1
fi

# 4. Execute SQLite-Aware Checkpoint with Strict Format and Frame Validation
echo "Executing PRAGMA wal_checkpoint(TRUNCATE)..."
CHECKPOINT_RES=$(sqlite3 "$DB_PATH" "PRAGMA wal_checkpoint(TRUNCATE);")
echo "Checkpoint Output: $CHECKPOINT_RES"

# Strict regex format check: ensure exactly three non-negative integers separated by pipes
if ! [[ "$CHECKPOINT_RES" =~ ^[0-9]+\|[0-9]+\|[0-9]+$ ]]; then
    echo "FATAL: Checkpoint output malformed: '$CHECKPOINT_RES'. Expected format 'busy|log|checkpointed'."
    exit 1
fi

BUSY_STATUS=$(echo "$CHECKPOINT_RES" | cut -d'|' -f1 | tr -d '[:space:]')
LOG_FRAMES=$(echo "$CHECKPOINT_RES" | cut -d'|' -f2 | tr -d '[:space:]')
CHECKPOINTED_FRAMES=$(echo "$CHECKPOINT_RES" | cut -d'|' -f3 | tr -d '[:space:]')

if [ "$BUSY_STATUS" != "0" ]; then
    echo "FATAL: Checkpoint failed with busy status $BUSY_STATUS. Active writers remain."
    exit 1
fi

if [ "$LOG_FRAMES" -ne "$CHECKPOINTED_FRAMES" ]; then
    echo "FATAL: Checkpoint incomplete: Log frames ($LOG_FRAMES) != Checkpointed ($CHECKPOINTED_FRAMES)."
    exit 1
fi

# 5. Post-Recovery Sidecar Inspection (Checking BOTH WAL and SHM sidecars)
if [ -f "${DB_PATH}-wal" ]; then
    WAL_SIZE=$(stat -c%s "${DB_PATH}-wal" 2>/dev/null || stat -f%z "${DB_PATH}-wal")
    if [ "$WAL_SIZE" -ne 0 ]; then
        echo "FATAL: WAL file size ($WAL_SIZE bytes) is non-zero after truncate checkpoint."
        exit 1
    fi
fi

if [ -f "${DB_PATH}-shm" ]; then
    SHM_SIZE=$(stat -c%s "${DB_PATH}-shm" 2>/dev/null || stat -f%z "${DB_PATH}-shm")
    if [ "$SHM_SIZE" -ne 0 ]; then
        echo "FATAL: SHM file size ($SHM_SIZE bytes) is non-zero after truncate checkpoint."
        exit 1
    fi
fi

INTEGRITY=$(sqlite3 "$DB_PATH" "PRAGMA integrity_check;")
if [ "$INTEGRITY" != "ok" ]; then
    echo "FATAL: Database integrity corrupted after WAL recovery: $INTEGRITY"
    exit 1
fi

FK_CHECK=$(sqlite3 "$DB_PATH" "PRAGMA foreign_key_check;")
if [ -n "$FK_CHECK" ]; then
    echo "FATAL: Foreign key violations detected after WAL recovery: $FK_CHECK"
    exit 1
fi

# 6. Revert Journal Mode to Approved DELETE Baseline & Verify Output
echo "Reverting journal mode to approved DELETE baseline..."
REVERT_OUTPUT=$(sqlite3 "$DB_PATH" "PRAGMA journal_mode = delete;" 2>&1 | tr '[:upper:]' '[:lower:]' | tr -d '[:space:]')
if [ "$REVERT_OUTPUT" != "delete" ]; then
    echo "FATAL: Reversion to DELETE mode failed. Returned: '$REVERT_OUTPUT'. Expected 'delete'."
    exit 1
fi

# Re-verify that sidecars have been removed by SQLite upon DELETE switch
if [ -f "${DB_PATH}-wal" ] || [ -f "${DB_PATH}-shm" ]; then
    echo "FATAL: WAL/SHM sidecars still present after switching journal_mode to delete!"
    exit 1
fi
echo "PASS: Reversion verified. Live journal mode is 'delete' and sidecars are absent."

# Enforce maintenance mode held
echo "======================================================================"
echo "CONTROLLED WAL RECOVERY COMPLETE: Database converted to DELETE mode."
echo "Application remains STRICTLY IN MAINTENANCE MODE."
echo "Next step: Execute Stage B Release Authorization or Canonical Restoration."
echo "======================================================================"
```

## 3. Production Rollback Protection & Non-Destructive Migrations

### 3.1 Pre-Deployment Rollback vs Post-Deployment Recovery
A strict distinction is established between development rollbacks and production recovery:
- **Pre-Deployment Rollback (Local / Staging)**: Standard `artisan migrate:rollback` may be tested in isolated sandbox environments prior to code deployment.
- **Post-Deployment Recovery (Live Production)**: Once deployed to production, **ordinary `artisan migrate:rollback` is strictly prohibited across all three migrations**.
  - Dropping `company_user` destroys multi-company dispatch mappings.
  - Dropping customer `classification` destroys verified regulatory taxonomy.
  - Dropping company branding columns destroys corporate identity and certification data.
  - In production, recovery must be accomplished either through **forward corrective migrations** or through the **canonical 16-step restoration procedure** documented in Section 2.5.
