## 3. Risk Analysis & Mitigation Matrix (Revision 4.6 Operational Standard)

| Identified Risk | Severity | Probability | Mitigation Strategy |
|---|---|---|---|
| **Stale Legacy `users.company_id` Access Leak** | High | Low | `authorizedCompanyIds()` resolves strictly from `company_user` pivot table. `users.company_id` provides ZERO authorization or fallback. Detaching pivot row immediately results in `403 Forbidden`. |
| **Public-Disk Media Exfiltration & Direct Static URL Leak** | High | Medium | Move all report photos and technical documents to `private` disk outside `public_html` (`storage/app/private/reports/`). Direct static requests return `404` or `403`. Serve strictly through authenticated streaming endpoint. |
| **Cross-Report Photo IDOR Vulnerability** | High | Low | In `ReportAssetController`, use relationship scoping: `$report->photos()->whereKey($photoId)->firstOrFail()`. Prevents requesting Photo B using Report A's authorized endpoint even within the same company. |
| **Sibling Directory Path Traversal in Media / Backups** | High | Low | Enforce separator-aware directory boundaries (`REAL_BACKUP_DIR_SEP="${REAL_BACKUP_DIR%/}/"` and `$baseWithSeparator = rtrim($realBaseDir, DIRECTORY_SEPARATOR) . DIRECTORY_SEPARATOR`). Rejects sibling directory prefix collisions (e.g. `backups_fake` or `photos/1_fake`). |
| **Shared LiteSpeed Hosting Writer Quiescence & Tool Limits (Finding 1)** | High | Medium | Clear operational reality: unprivileged user `u996219523` cannot inspect root or external LiteSpeed workers (`INSPECTION_UNAVAILABLE`). Operator assertion `CONFIRM_WRITERS_STOPPED=YES` alone does NOT establish quiescence. Mandatory external worker stop attestation artifact (`$STAGING_DIR/hosting_worker_stop_attestation.json`). Where Hostinger does not expose a verifiable worker termination API, restoration remains BLOCKED. |
| **Corrupt Live Database Overwrite during Restore** | Critical | Low | Direct `cp` to live database replaced with temporary staging file (`RESTORE_TMP`, `chmod 600`) located outside `public_html` on verified same filesystem. Staging file verified via SQLite `PRAGMA integrity_check` and `PRAGMA foreign_key_check` before executing atomic filesystem `mv`. Live DB set to `chmod 660`. |
| **Cross-Filesystem `mv` Degradation vs Same-Device Abort** | Critical | Low | If staging directory and live database reside on different mount points, `mv` degrades to non-atomic copy+delete, risking a corrupted live database if interrupted. Mandatory same-device validation via `stat -c %d` compares staging and live filesystems. Restoration halts immediately (`exit 1`) on mismatch with zero warning fallback. |
| **SQLite Sidecar Handling in DELETE Mode (Auto-Move vs Fail-Closed)** | Critical | Low | Unified policy: production baseline is strictly `delete` mode. Backup queries and normalizes `PRAGMA journal_mode;`, requiring exact `delete`. Sidecars in `delete` mode abort backup for investigation (no blind checkpoints, no `\|\| true`). In normal restoration, live sidecars trigger an immediate fatal abort; automatic moving or deletion of live sidecars is permanently prohibited. Exceptional WAL recovery is kept strictly separate in Section 2.6 with strict checkpoint format regex validation (`busy == 0`, `log == checkpointed`) and sidecar removal checks. |
| **Co-Located Checksum Self-Referencing vs Independent Trust Architecture (Findings 3, 4)** | High | Medium | Storing manifests in a separate local directory under `/home/u996219523/` does not constitute independent trust since the same unprivileged user has write access to both. Authentic cryptographic trust requires an off-server private signing key, on-server public key (`chmod 400`), and detached OpenSSL signature (`system_state.json.sig`) binding DB backup filename, byte size, and SHA-256 alongside membership manifest hash. Declared as an **UNRESOLVED OPERATIONAL DEPENDENCY / EXTERNAL DEPENDENCY** until infrastructure is provisioned. Manifest generation uses fail-closed queries (zero fallbacks) to dynamically capture User 1 role, applied migration names array, and migration count. |
| **Silent Media Downgrade vs Mandatory Deployment State Record (Findings 2, 5)** | High | Low | Private media deployment state is sourced strictly from a structured, cryptographically signed `.deployment_state.json` document with detached signature `.deployment_state.sig` verified against the release public key (no unsigned states). Contradictions between declared state and on-disk files abort immediately. Complete media scope verification computes relative path, byte size, and SHA-256 across all declared directories (`public` and `private/reports`) using safe null-delimited processing, unpacking archive to temporary staging outside `public_html` and diffing inventories bit-for-bit (symlinks, special files, and path traversals rejected). |
| **Restoration Lifecycle & Operator Release Separation (Finding 7)** | High | Medium | Canonical restoration procedure is split into two distinct stages: Stage A executes restoration and in-place verification (Steps 1–15), outputs durable receipt (`restoration_receipt_${TIMESTAMP}.json`), flushes caches, and concludes at Step 16 with the application locked in maintenance mode. Stage B executes independent operator release authorization via `./release_application.sh` after receipt validation and smoke tests. Documented authoritatively in Section 2.5 and Section 2.5.1 of `docs/CLIENT_CHANGE_DATA_MIGRATION_SAFETY.md`. |
| **Data Orphanage during Multi-Company Migration (Finding 9)** | Medium | Low | Migration pre-validation checks all 12 pre-conditions across all 8 accounts, verifies raw source tuples uniqueness before associative indexing to prevent key collisions, validates User 1 in a strictly read-only check, executes all mutations in a separate Transactional Mutation Phase within `DB::transaction`, and maintains syntactically validated single closure structure. Any unexpected account or role aborts migration immediately. Production rollback prohibited. |
| **Super Admin Role Semantic Confusion** | Medium | Low | `hasCompanyRole()` inspects actual `company_user` records only and never invents roles for Super Admin. Capability helpers (`canAccessCompany`, `canAdministerCompany`, `canPerformEngineerActions`) explicitly grant Super Admin bypass. |
| **Historical Site Inspection Data Loss** | High | Low | Two-tier fallback parser implemented in `formatSections()` and printable Blade template. If new keys are missing, old keys (`client_contact`, `main_incharge`, `site_incharge`, `caretaker_contact`) are mapped gracefully. |
| **Cross-Company Information Leakage** | High | Low | Query-level company scoping enforced in dashboards, search, lists, exports, downloads, and AJAX endpoints. Automated security test suite verifies strict isolation. |
| **Mixed-Role Privilege Escalation** | High | Low | Operational rights evaluated strictly per company via `company_user.role_in_company` and `canAdministerCompany($companyId)`. A global admin assigned as engineer in Company B receives `403 Forbidden` across all 6 administrative actions in Company B. |
| **Customer Phone Blank on Historical Reports** | Medium | Low | 3-tier fallback resolution: `report_data.phone_head` &rarr; `customer.phone` &rarr; `site.phone` &rarr; `—`. |
